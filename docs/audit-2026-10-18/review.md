审计日期：2026-10-18，Australia/Sydney。代码基线：`9ca84184da3d29eecb256daa6e2acee93cb6db08`。审计覆盖 `ctn/` 的 82 个 Python 文件、17,314 行，以及相关策略、配置、Pi 提示、SDK 适配和测试。没有修改业务源码，没有执行真实注册、发帖、回帖或举报。

## 1. 结论

**基础架构成立，执行状态的一致性明显好于简单脚本；但目前不能认定为可以直接无人值守参赛的完成品。**

最紧急的问题不是 SQLite 不够快，而是：

1. 正式原创发帖的正常 CLI 路径丢失 RAG 快照参数，会阻断战略发帖。
2. 回帖的“缺少上下文”状态跨模块传递有误，会在三次评估后被永久跳过。
3. 材料等待任务没有登记父帖等完整依赖，补到上下文后仍可能一直等待到过期。
4. 普通对方作者的等级未知时，普通价值回帖被挡住；高价值和认证目标则要求 `high` 账号，而新账号默认全部是 `standard`。这两条规则叠加，可能使对方回帖覆盖率很低。
5. 自动举报具有完整的局部门控，但正式服务没有连接裁决事件源。它目前是保守关闭的能力，不能算已经完成的自动闭环。

离线测试 **612/612 通过**。这说明大量合同校验、故障恢复和边界处理是有效的，不能证明模型判断准确、能改变 NPC 观点，或正式服务器能走通所有入口。此次新增复现恰好找到了现有测试没有覆盖的入口和状态衔接问题。

以下严格分为“可复现缺陷”“条件性阻断/能力边界”和“策略取舍”；不把这些统称为 bug。

## 3. 已确认的代码缺陷

### F1 · P1：CLI 战略发帖丢失 RAG 快照

位置：[publisher.py:234](/Users/shaelyn/Documents/Projects/CNT2026/ctn/macro/publisher.py:234)，调用方 [cli.py:132](/Users/shaelyn/Documents/Projects/CNT2026/ctn/macro/cli.py:132)。

`cmd_publish()` 把 `--rag-snapshot` 传给 `publish_sync()`，后者虽然接收 `rag_snapshot_id`，调用异步 `publish()` 时却没有继续传递。实际发布函数在真实客户端、非 dry-run、非 warmup 时要求该参数。

**复现：**同一人设、正文、有效快照，使用无网络的模拟发送边界：同步入口返回 `blocked / rag_snapshot_required`；直接调用异步入口返回 `published`。它不是模型保守拒绝，也不是服务器未开放造成的。

**影响：**按 Pi 技能给出的标准 CLI 操作，所有走到 RAG 检查的正式战略原创都会被拦下。异步 Python 暖号入口不受这一参数问题影响。

**修复方向：**透传这个参数；补一条覆盖 `CLI → publish_sync → publish` 的有效快照集成验证。不要只测异步发布或 mock 下自动补快照的情况。

### F2 · P1：缺上下文被当成普通评估失败，三次后永久跳过

位置：[actions.py:128](/Users/shaelyn/Documents/Projects/CNT2026/ctn/jev/actions.py:128)、[brain.py:311](/Users/shaelyn/Documents/Projects/CNT2026/ctn/pipeline/brain.py:311)、[loop.py:230](/Users/shaelyn/Documents/Projects/CNT2026/ctn/pipeline/loop.py:230)。

实际链条是：

`flow.status=needs_context → action.status=needs_assessment → rationale=jev:needs_assessment`

但循环进入材料等待分支时匹配的是 `jev:needs_context`。因此这些任务走普通重试。任务领取方法返回的是递增前的 `attempts`，循环在第三次评估时达到跳过条件。

**复现：**通过真实 `JevWorkflow + JevLlmBrain + BotLoop`，只用合成 Jev 响应表达缺上下文；三次处理后数据库为 `status=skipped, attempts=3, reason=jev:needs_assessment`。

**影响：**评论先于父帖到达、材料解释依赖尚未抓到的内容时，会浪费重复评估，随后失去本可恢复的回帖机会。类似的 `jev:needs_materials` 也不在显式等待前缀列表中。

**修复方向：**传递结构化状态和 `needs`，保留“缺材料/上下文”和“传输失败”的区别；不要让展示用的理由字符串决定生命周期。

### F3 · P1：等待指纹缺少父帖等依赖，材料到达后不恢复

位置：[operations.py:47](/Users/shaelyn/Documents/Projects/CNT2026/ctn/storage/operations.py:47)。

`dependency_fingerprint()` 只包含目标 ID/版本、语料哈希、背景版本及目标 raw 中的三个作者字段。它没有包含父帖 ID/内容版本、引用上下文，以及独立账号登记中的认证更新。恢复函数只比较这个指纹。

**复现：**子帖进入 `waiting_materials` 后补入父帖，父帖确实存在，但指纹完全不变，子帖仍为 `waiting_materials`。

**影响：**即使修复 F2，部分等待任务仍无法自动被唤醒。这是队列依赖设计问题，不是 SQL 执行速度问题。

**修复方向：**显式登记任务依赖对象和版本；相关父帖、作者信息或材料发生有效更新时重新入队。避免用无意义的抓取时间变化触发所有任务重评。

### F4 · P2：对方帖子用途选择会让情绪关键词盖过真正问题

位置：[brain.py:234](/Users/shaelyn/Documents/Projects/CNT2026/ctn/pipeline/brain.py:234)。

对方帖子没有使用中立/混合帖的独立用途判断，而是本地选择。`worried`、`concern`、`my family` 等关键词检查在 `func == question` 之前；`func == concern` 又不是当前 `expression_function` 的枚举值。

**复现：**“I'm worried about the ferry rule. What do the trials actually establish?”，即使 Jev 已把中心功能判为 `question`，仍选择 P07 而不是 P02。

**影响：**可能先安抚而不直接回答证据问题，和题库的“中心真实问题优先”不一致。P07 提示仍要求回应实质内容，所以不能据此断言每次都会答非所问；问题在选择优先级。

**修复方向：**中心问题先于附带情绪；用 `direct_question`、`concrete_concern` 等已有判断，或统一用途选择。不要继续增加孤立关键词。

### F5 · P2：模型可选用途与真实执行能力不一致

位置：[response.v1.json](/Users/shaelyn/Documents/Projects/CNT2026/ctn/jev/rubrics/response.v1.json:1)、[brain.py:320](/Users/shaelyn/Documents/Projects/CNT2026/ctn/pipeline/brain.py:320)。

中立/混合帖的用途模型可选 P02–P09；实际 Brain 只支持 P01、P02、P03、P07、P08。模型若选择 P04/P05/P06/P09，就直接得到 `unsupported_purpose:*`；循环将其跳过。

**复现：**合成模型选择 P04，实际 Brain 返回 `action=none / unsupported_purpose:P04`。

**判断：**缺少比较材料或人工核验时不擅自执行，是正确的。但让模型持续选择生产路径根本无法承接的用途，会产生稳定死路。不能把底层 MaterialChecker 有九种用途当成主循环九种用途全部可用。

**修复方向：**明确向决策层声明当前能力，或把这些结果持久化为可补材料/可人工审阅任务；不要为了覆盖率自动降级成不匹配的 P08。

### F6 · P2：非默认 Jev 模型配置不能通过主服务装配

位置：[main.py:73](/Users/shaelyn/Documents/Projects/CNT2026/ctn/main.py:73)。

客户端用 `settings.jev.model`，但显式创建的 `JevPacker` 没有传 `model`，仍默认为 `jev-latest`。`JevEvaluator` 随即检查两者必须一致。

**复现：**配置任意不同模型名时抛出 `EvaluatorValidationError: model: client and packer must agree`。

**影响：**默认模型不受影响；切换或固定具体版本时服务会启动失败。修复应传同一个配置值，而非删除一致性检查。

### F7 · P2：输入完整性标记被硬写为 true

位置：[brain.py:204](/Users/shaelyn/Documents/Projects/CNT2026/ctn/pipeline/brain.py:204)。

`payload_for()` 对目标和父帖都直接写 `text_complete=True`，没有保留上游明确提供的 false 或未知。**复现：**输入目标和父帖均标记 false，实际送评 payload 的两个标记都变成 true。

这会绕过输入合同原本支持的“内容可能截断”语义。SDK README 还将通知中的 post 称为 trimmed 对象，并建议 `get_post()` 取完整帖子；这并不能证明正式通知的正文一定被截断，但说明通知摘要不能无条件被认定完整。若截断位置涉及否定、引用或条件，机会和立场判断会受到影响。

**修复方向：**只在来源合同或完整详情请求能够证明时声明完整；保留已有完整性标记，对必须依赖全文的通知按需补取详情。

## 4. 条件性阻断与尚未接通的能力

### C1 · 高优先级：对方作者等级与己方 high 账号供应需要实际解决

位置：[legit_v1.py:331](/Users/shaelyn/Documents/Projects/CNT2026/ctn/client/legit_v1.py:331)、[actions.py:155](/Users/shaelyn/Documents/Projects/CNT2026/ctn/jev/actions.py:155)、[router.py:94](/Users/shaelyn/Documents/Projects/CNT2026/ctn/persona/router.py:94)。

当前规则：对方 `reply_value < 1` 跳过；`1 ≤ value ≤ 3` 且目标等级未知时等待账号信息；`value > 3` 或目标被映射为 high 时要求己方 high 账号。

适配器对没有明确等级、没有认证的作者返回 `unknown`，不会从用户名猜等级。这个处理诚实，但没有生产中的主动等级补齐流程，等待指纹也不包含等级映射版本。**如果正式 API 只提供普通作者/认证标记、不提供本项目期待的等级标签，中等价值的对方帖会系统性卡住。**官方入门示例不足以证明正式响应含有等级字段，必须开服后看真实数据，不能现在声称已经兼容。

同时，新绑定账号的 capability 全部默认 standard；医生/律师人设也不会自动成为 high。实际复现：两个已激活 standard 账号无法承接一个 high 要求的目标。这是设计中的显式运营设置，不是绕过校验的 bug，但必须完成才有对应产能。

建议先明确 high 的业务含义、实际可验证的标签映射和己方可用供应。不要为通路而把 `unknown` 伪装成已知，也不要把职业身份等同于平台权限。如果“high”只是本地质量角色而非官方权限，应明确按该含义管理。

### C2 · 高优先级：自动举报没有真实裁决事件源

位置：[main.py:81](/Users/shaelyn/Documents/Projects/CNT2026/ctn/main.py:81)、[events.py](/Users/shaelyn/Documents/Projects/CNT2026/ctn/moderation/events.py:1)、[operations.py:160](/Users/shaelyn/Documents/Projects/CNT2026/ctn/storage/operations.py:160)、[ops.py:113](/Users/shaelyn/Documents/Projects/CNT2026/ctn/ops.py:113)。

主服务硬接 `UnavailableModerationSource`；manual clearance 命令只签发五分钟放行，并明确写 `live_source_verified=False`。因此通过现有生产入口，单改 `CTN_REPORT_MODE=hybrid` 不能得到自动举报闭环。`CTN_AUTO_REPORTS` 也不是有效的自动开启开关。

manual 模式需要候选批准和放行都有效；裁决可人工导入。pending 上限会使没有裁决输入的系统停止继续举报，避免失控。这是合理的保护，但比赛计划里应写成“待接口确认 / 人工运行”，不能写成“自动蓝队已上线”。

另外，`confirmed_activity` 的动作总数依赖人工导入；抓取发帖次数不等于账号全部动作数。`true_team_id` 也没有正常生产填充通路，所以按真实队伍计算递减收益的排序通常缺信息。保留未知是对的，只是不能期待这两项优化自动生效。

### C3：原创自动调度与阶段切换在进程外

Pi pulse 的周期运行需要外部调度；Compose 只启动 Python fleet。README 中的 cron 是示例，并不是仓库内可自动生效的调度器。此次没有读取或修改用户系统 crontab，因此不能断言外部已经配置或没有配置。

`harness.md` 仍写着 10 月 14 日的 Phase 1 和已过去的叙事锁时间。SQLite 的 phase 和 harness 文本是两套状态，服务不会按日历自动同步，也不会自动激活账号。现场必须明确由谁推进阶段，以哪一个状态为准。

本地 `.env` 白名单检查可确认 dry-run 为 true、账号上限配置为 40；未见文件内的 `CTN_SIDE` 或 `CTN_REPORT_MODE`。shell/容器环境及命令行可能覆盖它们，因此这不是对其他部署状态的判断。对本机默认启动而言，应显式设置 YES；要部署 50 个账号时也应先处理 40 的本地上限。

### C4：外部 Jev 的用途存在规则解释待确认项

规则 5.1 对外部 AI 的例外明确写的是创意内容生成，5.2.1 的例子也是生成帖子/评论。当前 Jev 的主要用途是外部分类、路由和发送复核，不能仅凭这些条文就确定它也属于该例外。与此同时，规则也允许 AI 自动化和分析比赛数据，因此本审计**不据此判定违规**。如果团队已有组织方对外部决策/评审 API 的明确确认，应以该确认和最终规则解释为准；此次未见这份确认，建议列为开服前待闭合事项。[官方规则 5.1、5.2.1、6.1](https://capturethenarrative.com/info/competitions/2026/rules/)

## 5. 发帖、回帖、举报策略是否合理

### 发帖

合理之处：绑定且激活的账号才能写；人设版本、配额和原帖锁统一在 SQLite；来源区分官方事实、归属某人的主张、论证和未知；来源快照可撤回；趋势状态保留 unknown。这些限制直接减少事实乱编、身份冲突和重启重复发送。

主要局限：

- 宏观分支是 Pi 提示规则，没有平台反馈证明 A/B 分支的收益。排名前 20 条是样本，不能推断全民立场。技能已承认这个边界，代码也没有自动统计所谓全站多数，处理正确。
- B 分支优先扫描拒绝、情绪、攻击，再扫描真实问题，可能把稀缺原创名额花在争吵中心。对方不应答复时转为独立论证的分支有价值；具体优先级仍需实测。
- `branch_B_1b` 的发前规则仍写着“指出情绪操纵”，但最新 Pi 技能要求不猜动机，存在提示不一致。对有合理顾虑的发言指控操纵，可能适得其反。
- 本地战略原帖上限 10/日、同号原帖锁 24 小时，都是己方策略，不是官方要求。暖号另限 15/日，且每号暖成功一次才放行常规回帖。50 个新号若都需要暖号，单靠这份配额至少跨四个悉尼自然日；30 个号至少两日。暖号还触发该号 24 小时原帖锁，但回复只受短冷却影响。
- 官方入门当前允许 500 字符，本地发前和存储共同硬限 280。这是保守风格选择，不是违反规则；如果团队以为官方只能 280，应纠正。复杂限定与证据可能需要更多空间。[官方入门](https://capturethenarrative.com/info/competitions/2026/getting-started/)

判断：**发布安全性思路合理，选题收益仍是假设；先修 F1，再谈分支优化。**

### 回帖

合理之处：立场针对当前内容而非永久作者归属；区分支持疫苗与支持公共空间准入要求；真正的中立/混合帖有独立决策；材料和评估目标绑定；生成后再审；失败最多定向重写一次；不把模型计划计为已执行。

需要改进的决策效率：

- 任务以 `next_attempt_at, post_id` 排队，每批最多评估 8 个，等待整批 `gather` 结束，再推进。没有按预期价值、时效和成本排序；慢任务会拖住同批快任务的发送。
- 抓取不是完整全站镜像：frontline 每次取一页最新帖，默认 30 条，不持久化 feed 游标；关键词搜索在找不到标签时也只过滤最新一页。两次有效读取之间若出现超过一页的新帖，一部分可能永久漏掉。评论分页做得比这个完整；热门评论优先也不能保证低热度线程永不饥饿。
- 主路径只有 like/reply/no interaction；没有自动 repost/follow 的策略分支。接口存在不等于策略启用，mock 中的 repost 不能用来证明正式运行覆盖。
- 同阵营回复使用帖子 ID 哈希约三分之一抽样，再限制全队每小时 3 条；这是确定性抽样而非每第三次观察。控制回音室是合理的，但也可能错过高质量支持者问题。降级 like 依然消耗写请求，不是免费动作。
- 多回复信号要求“至少两条有不同实质贡献”，概率达到 0.90 才可能扩展；随后却随机抽取 1–3 个额外账号，可扩到四条。每条新增内容复核会挡掉无价值扩展，但模型预算仍可能白花。应按可支持的新贡献数量决定，而非仅按随机条数。
- 内容机会分数和立场最高概率标签不是实际说服收益；立场分支也没有统一的最低概率/差距门槛。现有 1/2.5/3 阈值是本地规则，尚无本赛场校准证明。中立用途选择的 0.70 门槛不能自动覆盖立场误判。
- `payload_for()` 通常只提供直接父帖和己方最多 20 条互动，没有完整线程或其他人的现成回答。Jev 判断“是否已经有人说过”或“还有几条互补贡献”时，看到的上下文有限。RAG 检索也主要用目标短文本，代词式回复容易失去父帖主题。
- RAG 是静态词法检索，加领域词汇和完整依赖保留，并非自动吸收新新闻的知识系统。归档/claim 表具备接口，不代表新闻已经被自动核验并进入生成语料。52 个检索验收样例通过不等于开放文本泛化已经验证。

模型调用成本也应算进去：通常的对方回复至少是 triage、deep、postflight 三次 Jev 加一次 LLM；中立/混合再多一次用途判断。每个额外回复又需要生成与复核，重写和传输重试另算。TypeSafe 的文章支持“结构化决策”这种用途，但其速度/校准宣传不能证明本项目的题库、检索和发送策略准确。[TypeSafe 原文](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

判断：**微观内容约束较扎实，任务恢复和实际可达性有硬问题；当前更接近受控回复流水线，还不是经过效果校准的最优调度器。**

### 举报

合理之处：

- 己方与认证账号受保护；缺字段不冒充零；证据家族封顶，不能靠无限重复同一信号堆分。
- 至少 85 分并有两个实质证据家族才具备候选资格。代码明确这不是“85% 是机器人”。
- 自动白名单比一般候选更窄：目标泄漏信号，加至少两个其他帖子/线程中的独立重复或协同行为；引文/代码示例会被剥离后再判断。
- 候选、批准和发送均绑定证据哈希与版本；限 pending；明确裁决才记结果，拒绝时启动全队六小时停报。404 不被解释为“举报成功”。
- 裁决按 report/attempt 绑定并去重；账号举报被 dismissed 后不倒补得分，重新申请要求等待和新证据。这些处理符合延迟裁决的性质。

主要局限：

- 判定关注“像不像机器人”，而官方 Blue 分以裁决为准。官方明确裁决存在约四分之一误判，即使识别到真实对手机器人也可能触发停报。自动阈值高不等于没有裁决风险。[官方计分：举报](https://capturethenarrative.com/info/competitions/2026/scoring/#3-reporting-inauthentic-posts-and-accounts)
- 静态分数没有校准成命中率，也没有把停报机会成本、剩余赛时、首报概率和迟延裁决纳入统一收益排序。按真实队伍递减收益排序因 C2 的输入缺口通常失效。
- 泄漏+长期行为的自动条件很保守，能减少误报，也会漏掉没有露馅的成熟机器人。保守不是错误，但 Blue 预期收益不能按“高召回自动猎杀”估算。
- 不是只举报 NO 方：扫查没有阵营过滤，会处理其他 YES 队伍。比赛是队伍得分竞争，但也有阵营收益；这是一项应明确决定的策略，而非默认等同于最优。
- 结赛条件只检查“已经结束”，没有检查是否还来得及等裁决。末段新举报的收益需要单独评估。

判断：**证据与状态处理比进攻性收益优化成熟；正式自动能力尚未接通，当前应按人工辅助模式评估。**

### YES 方的计分方向

本项目正确地将目标限定为“是否要求接种证明才能进入公共空间”。仅说明疫苗有益，未必回答公投。官方对 NPC 向己方转变给 160 基础分、反向转变扣 80；首个成功帖子举报为 25，后续报告通常为 5，且存在递减和停报风险。因此，从计分权重推断，应优先保证有证据、能回应实质问题的发言，再优化举报数量；不能把模板化同意、点赞数或发言量视作胜利指标。此处是基于规则的推断，不是已观测到的策略效果。[官方计分](https://capturethenarrative.com/info/competitions/2026/scoring/)

YES 的合理论证空间是预防、医疗承载和共同风险；官方设定仍保留传播效果、保护持续时间等不确定性。代码区分事实、论证和未知的方向正确，应保留，避免把“不确定”写成“已经证明无风险/必然避免封锁”。[官方设定](https://capturethenarrative.com/info/competitions/2026/setting/)

## 6. SQLite 逻辑与一致性

### 做对了的部分

1. **短事务、真实发送不在事务内。**外层 `BEGIN IMMEDIATE`，嵌套块有 SAVEPOINT；Python 线程共享连接由 RLock 保护。事务回滚与跨进程领取已有测试。
2. **发言采用先记意图再发请求。**action_key、账号租约、队列 owner 和版本共同防止并发抢发；成功后一次事务内更新账号、互动、publication 与采样任务。
3. **UNKNOWN 保守处理。**发送后超时不盲目重试；账号租约保持占用，只凭精确作者历史中的正证据恢复，或者人工处理。它牺牲可用性换取防重复，比赛中是可以解释的选择。
4. **发送前二次检查。**模型生成和限速等待之后再确认目标版本、期限、配额、人设、撤回材料与批准有效性，减少检查后状态改变的问题。
5. **配额计入预留和未知。**悉尼日界限、帖子与账号举报、实际裁决日期等不是仅凭内存计数；重启不会无故重置这些状态。
6. **采样缺失保持未知。**nullable 指标、来源、采样窗口与实际年龄被记录，没有用总互动假装 NPC 互动或说服得分。
7. **迁移前备份、备份 API、schema 版本和目录权限**都有实现。没有发现需要为了这场比赛更换数据库产品的证据。

### 需要接受或调整的取舍

- 同一 Store 的所有访问受一个 RLock 串行化；WAL 不会让这条连接变成多写者。部分 getter（如 `get_account_state`）也进入 `BEGIN IMMEDIATE`，读已存在状态仍会竞争写锁；短期不是大问题，负载上来后应分离纯读与初始化。
- 表间大多依靠应用校验而非 FOREIGN KEY。通过正式执行路径，一致性控制较完整；绕过方法直接改表不能享有同样保证。
- `synchronous=NORMAL` 是性能/持久性的取舍。SQLite 官方说明 WAL+NORMAL 在断电或硬重启后可能丢失最近已提交事务；关键发送意图若丢失，业务层的防重承诺也会受影响。常规进程崩溃恢复不能代替断电持久性证明。若比赛更重视不重发，可评估 FULL 并在部署磁盘重测。[SQLite WAL 文档](https://sqlite.org/wal.html)
- 请求尝试、任务、日志和效果采样会累积，当前没有完整保留/压缩计划。需要监控磁盘、WAL 与历史任务规模；保留审计数据的同时归档冷数据。
- UNKNOWN 在有限历史里找不到就不会自动判失败，账号可能长期不可用。这个保护合理，需要可操作的人工恢复流程；不能用“没在前 50 条找到”当作未发送证明。
- Heartbeat 的 alive 和业务进度不是效果指标；read 的空列表回退、skipped 更新进度以及未纳入 stalled 的部分状态，都可能使“健康”弱于“持续有效工作”。应同时观察成功发送、有效观测、跳过原因与未知占用。

## 7. SQLite 实测速度

环境：Python 3.14.6、SQLite 3.53.3、macOS 本地临时文件、WAL/NORMAL、热缓存。每组 1,000 作者，5% 本地 confirmed 标签。**没有把这些结果当成 2 CPU / 1 GiB 容器、冷盘或官方服务器下的保证。**

| 操作 | 10 万帖子 | 100 万帖子 |
|---|---:|---:|
| 单帖主键查询 P95 | 0.0070 ms | 0.0070 ms |
| 作者最近 20 帖 P95 | 0.1538 ms | 0.0927 ms |
| 文本哈希查重 P95 | 0.0180 ms | 0.0176 ms |
| 评论队列前 15 条 P95 | 0.1065 ms | 0.0875 ms |
| confirmed 文本库 150 条 P95 | 1.6799 ms | 3.6576 ms |
| runtime_metrics P95 | 4.2702 ms | 43.6698 ms |
| 首轮大批过期任务清理（单次） | 136.34 ms | 1,504.08 ms |
| 清理后领取 8 个任务 P95 | 0.1066 ms | 0.1094 ms |
| 30 条新帖入库＋检测（单批） | 3.270 ms | 2.999 ms |
| 数据库主体大小 | 75.43 MiB | 782.75 MiB |

作者查询的十万组偶发波动高于百万组，不能由一次 P95 倒推出百万规模更快。关键是两者都很小。整批 30 条检测约 602 条 SQL，但只有一次 COMMIT；这解释了“语句不少，仍然较快”。confirmed 库查询确实使用临时 B-tree 排序，当前测量仍为毫秒级，优先级低于逻辑缺陷。

### DB-P1（优化优先级，不是数据损坏等级）：活跃回复批次导致重复扫描

路径：[runtime.py:433](/Users/shaelyn/Documents/Projects/CNT2026/ctn/storage/runtime.py:433) → [campaign.py:214](/Users/shaelyn/Documents/Projects/CNT2026/ctn/storage/campaign.py:214)。每个新帖入库都会调用 `_expire_reply_batches()`，后者遍历所有 active/paused 批次，并逐条读取目标帖。

补充文件型测试只改变活跃批次数，测量真实 Store 的 30 条入库+检测，五轮中位数：

| 活跃批次 | 30 条入库耗时 | 单轮 SQL 数 |
|---:|---:|---:|
| 0 | 2.430 ms | 602 |
| 50 | 12.138 ms | 2,102 |
| 200 | 41.767 ms | 6,602 |
| 500 | 100.302 ms | 15,602 |

这是可以复现的 **新帖数 × 活跃批次数** 放大，而且发生在写事务内。500 批次并不表示实战一定达到该规模；它用于暴露原有“帖子很多但没有活跃批次”基准看不到的路径。100 ms 当前也不意味着数据库不能用。

建议：过期批次按 `expires_at` 索引批量处理；目标版本改变时只取消相关目标；正常扫描移到独立低频维护步骤。然后重测“有活跃批次＋Pi 同时发布”的混合负载。

**速度总判断：SQLite 在当前请求速率下够用。真正瓶颈更可能是官方写配额、模型调用、排队和业务门控。优先修状态，再优化批次扫描；没有依据现在迁移 PostgreSQL。**官方当前将发帖/回复/转发合并为全队 3 次/分钟，feed 为全队 10 次/分钟；因此 1.5s/2.5s 是工作循环设定，不是可兑现的独立 API 吞吐量。HTTP Pacer 对共享路由计数的方向正确。[官方入门限速](https://capturethenarrative.com/info/competitions/2026/getting-started/#rate-limits)

## 8. 开服前的处理顺序

1. 修 F1；用正常 CLI 在合成真实模式边界证明快照真正到达发布器。
2. 合并修 F2/F3；覆盖“先抓子帖，后抓父帖”和“Jev 要求材料，材料后来到达”的恢复链。
3. 明确 C1：等级映射、high 角色与供应、warmup/phase 的真实可执行配置。别等模型请求 high 时才发现没有账号。
4. 解决 F4/F5，统一用途优先级与真实支持范围；校验非默认模型装配 F6，修正输入完整性标记 F7。
5. 把原创外部调度、账号激活、阶段推进和人工裁决导入变成可演练的运行步骤。
6. 开服后最小规模验证实际响应、字符限制、限速反馈、ID/父帖字段、认证字段、裁决来源和账号动作计数。官方说明 2026-10-19 17:00 悉尼时间开放相关操作，因此本次没有用不存在的正式联调结果作结论。[官方入门](https://capturethenarrative.com/info/competitions/2026/getting-started/)
7. 再收集真实采样反馈，比较有用回答、同阵营互动和多回复的收益；最后优化批次扫描与历史归档。
