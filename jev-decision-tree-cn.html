00两棵树所处的位置

两棵树都是解析后 JEV 响应的纯函数。它们都不接触平台、账号或 LLM——只负责决策， 并记录决策理由。

校验输入→ 注入预检
（离线，无网络）→ 打包→ JEV 初筛 · 4 个问题→ TREE 1→ JEV 深度评估 · 17 个问题
条件触发→ TREE 2→ 交接
execution_authorized=False
唯一的不变式 每次交接都携带 execution_authorized=False。一个就绪的生成任务只为下一个模块提供 素材，从不授权发布。

01树 1 · 路由 —— 该走哪条评估路径

RoutingPolicy.decide() · 首个匹配即命中 · 自上而下依次求值。

1
parsed.status == "failed"  或  error is not None  或  output is None
→ failed evaluation_failed
2
prompt_injection 答案缺失  或  类型不是 noul
→ review risk_unavailable  ·  风险缺失绝不等同于风险为零
3
prompt_injection  ≥ 0.5
→ review injection_signal  ·  阈值 injection_review_threshold
4
relevance 缺失、类型错误，或不属于 {relevant, unrelated, unclear}
→ failed relevance_unavailable  ·  有意判为 failed 而非 unrelated：答案缺失时绝不能静默丢弃一条帖子
5
relevance == "unclear"
→ deep relevance_unclear  ·  由 unclear_to_deep = true 控制
6
relevance == "relevant"
→ deep relevant
7
P(unrelated)  ≥ 0.8
→ observe clearly_unrelated  ·  完全跳过深度评估 · 阈值 unrelated_min_probability
8
其余情况 —— unrelated 标签但概率低于下限
→ deep weak_unrelated_signal
注意这里的顺序 风险检查排在相关性之前，因此即使一条帖子本会因不相关而被丢弃，也仍会被扫描是否含注入。 在这一阶段，账号等级和互动量不参与帖子的过滤。

02树 2 · 行动 —— 点赞、回复，还是什么都不做

ActionPolicy.decide() · 阶段 A 先执行并短路；只有通过守卫的才会进入分数比较。

阶段 A · 守卫（首个匹配即命中，此时还不读取任何分数）

A1
route == "review"  或  flow.status == "needs_review"
→ needs_review action=None assessment_requires_review
A2
flow.status ∈ {failed, deferred, needs_context}  或  route == "failed"
→ needs_assessment assessment_unavailable
A3
route == "observe"  且  flow.status == "observe"
→ decided action=no_interaction clearly_unrelated
A4
flow.status ∉ {evaluated, partial}  或  flow.deep is None
→ needs_assessment deep_assessment_required

阶段 B · v2 委托

B1
relative_stance ∈ {neutral, mixed}
→ needs_llm_assessment downstream_response_planning_required
不选择任何行动，也不选择任何账号。由下游的 LLM 决定是否回应以及回应什么。 中性措辞不意味着高说服可能性。
B2
relative_stance 既不是 aligned 也不是 opposing
→ pending_rules alignment_action_rules_pending

阶段 C · 分数闸门

C1
答案缺失  或  type ≠ score  或  legend ≠ 恰好 {0,1,2,3,4}
→ needs_assessment action_score_unavailable  ·  分数不可用时绝不回退到默认值
C2
aligned  →  读取 response_specificity   |   opposing  →  读取 reply_value
这是两个不同的信号。response_specificity 衡量回应要点能被多明确地识别； reply_value 则是一个独立的回应机会评分。

阶段 D · 阈值

D-1 · aligned

1
response_specificity  > 2.5
→ decided · reply aligned_specificity_above_threshold · quality=ordinary
2
response_specificity  ≤ 2.5
→ decided · like aligned_specificity_not_above_threshold

D-2 · opposing

1
reply_value  < 1.0
→ decided · no_interaction opposing_value_below_threshold
2
reply_value  > 3.0
→ decided · reply opposing_high_account_required
required_account_level=high · minimum=high · reply_quality=high
3
1.0 ≤ reply_value ≤ 3.0  →  按目标账号的平台等级分支
platform_level 映射为结果
highdecided · reply high / high / high
unknown（或未映射）needs_account_metadata action=reply · opposing_target_level_unknown
standarddecided · reply opposing_standard_reply · ordinary
高等级目标救不回一次跳过 高等级升级的判断晚于 reply_value < 1.0 这道闸门，因此即便目标账号级别很高， 只要回应机会没有价值，依旧会被跳过。

03边界语义

由 tests/test_jev_actions.py 锁定，而不是靠文字约定。下面这些用例一旦比较符在 > 与 ≥ 之间翻转，就会静默失效。

信号取值结果说明
response_specificity0likealigned，远低于门槛
response_specificity2.5like恰好等于阈值 → like
response_specificity2.5001reply需要严格大于
response_specificity4reply最大值
reply_value0no_interactionopposing
reply_value0.9999no_interaction仍然低于下界
reply_value1reply · standard下界包含端点
reply_value2reply · standard普通区间
reply_value3reply · standard恰好为 3 仍属普通区间
reply_value3.0001reply · high需要严格大于
reply_value4reply · high最大值
值得记住的不对称 aligned 阈值使用 >（2.5 → like），而 opposing 的下界使用包含端点的比较 （1 → reply）。分数是小数，所以这两个边界都不是理论上的假设。

调用方必须逐层检查。HTTP 响应成功并不意味着评估可用，也不意味着任务就绪。

05默认值与已知缺口

有两个默认值决定树 2 是否真的采取行动。二者都是刻意为之，且都需要外部输入。

配置项默认值后果
platform_levels {} 普通区间内的每条 opposing 帖子都会返回 needs_account_metadata， 而不会派发回复。在提供真实的标签映射之前，这条路径不会做任何事。
pending_rules ['engagement_trigger_thresholds'] 互动量没有独立的触发器。可见的点赞和转发只能定性地影响 reply_value；它们本身永远不会推翻某个决策。
mixed_neutral_policy downstream_response_planning 中性和混合的帖子不会继承 opposing 帖子的价值阈值——它们被委托给下游处理。

修改阈值

它们是冻结的 dataclass 字段，而不是散落在代码各处的字面量：

from ctn.jev.routing import RoutingPolicy
from ctn.jev.actions import ActionPolicy

routing = RoutingPolicy(
    unrelated_min_probability=0.8,     # Tree 1 step 7
    injection_review_threshold=0.5,    # Tree 1 step 3
)
actions = ActionPolicy(
    aligned_reply_above=2.5,          # D-1
    opposing_reply_from=1.0,          # D-2 lower bound (inclusive)
    opposing_high_above=3.0,          # D-2 upper bound (strict)
    platform_levels=(( "<real label>", "high" ),),
)
每一次改动都可追溯 两个策略都暴露一个 fingerprint（规范化配置的 sha256）。审计事件会记录 每个决策由哪个指纹产生，因此事后可以回答：「那条回复发出时，生效的是 哪套阈值？」
尚未实现的部分 树 2 决定的是需要哪种互动，以及需要什么账号等级。它不挑选具体账号、 不生成文本，也不发布。这些属于下游的账号 / LLM / 审核模块， 而它们目前尚不存在。
