01Summary

Before this change the bot loop was a single function that called the platform directly, bypassing the rate limiter. Now there is one gateway for all platform calls, and the loop is split into small stages that can each be replaced independently.

The one rule to remember Nothing talks to the platform except ctn/actuator.py. Every like, comment, retweet, post, follow and every read goes through the Actuator, which applies rate limiting, budget accounting, retries and dry-run. If you call client.like(...) directly, you skip all of that and risk getting accounts suspended.

02How a cycle works

One call to BotLoop.run_cycle() runs the whole read → react → act sequence once. run_forever() repeats it on a timer.

READpipeline/perceive.pyuses read budget
perceive() → Observation
  • 1 trending call (top 10 hashtags)
  • 1 search per keyword (default: kingstonia, h2d2, vaccine, public spaces) plus the top 2 trending hashtags
  • Converts results to Post objects and removes duplicates
  • When the read budget runs low (ledger.read_pressure > 0) it drops the lowest-priority queries first
↓ list of Post (minus posts we already acted on and posts by our own bots)
REACTpipeline/decide.pyno network
decide(post, side=…) → Decision
  • Scores relevance (keyword hits + engagement) and alignment (+1 our side … −1 their side)
  • Picks one action: like, repost, reply, or observe (do nothing). Rules in section 04
  • For replies, gets text from compose.py
↓ actionable decisions, highest relevance first, at most 3 per cycle
ACTpipeline/loop.pyuses write budget
Assign a bot → check text → execute through the Actuator
  • Bots are used in rotation (round-robin), one bot per action; suspended bots are skipped
  • Reply text goes through check_text(); empty or > 280 characters is blocked
  • Successful targets are remembered so the fleet never acts on the same post twice
  • If the cycle had no throttling, the rate limiter is allowed to speed back up (section 08)
↓ CycleReport
RESULTreturned + logged
CycleReport
  • status: "idle" (nothing found), "observed" (found posts, no successful action), "acted"
  • observed: number of posts read · decisions: every Decision · results: one ActionResult per action attempted

03Action functions — ctn/actuator.py

These are the functions the team asked for. All are async. Write actions return an ActionResult; they never raise for normal platform problems. Check result.ok and result.detail.

Write actions

FunctionAlso calledWhat it doesScore channel
like(account, post_id)Like a postStory (spread)
repost(account, post_id)retweetShare a post to the bot's followersStory (spread)
reply(account, post_id, text)commentReply under a postEngagement + Story
post(account, text)New original postEngagement + Story
follow(account, target)Follow a user(reach)
unfollow(account, target)Unfollow a user—

Every write also accepts an optional decision_id= so the action can be linked back to the decision that caused it in the logs.

Read functions

search(query), trending(), get_post(id), get_comments(id), get_feed(account), get_mentions(account), get_profile(handle). On failure they return an empty list / dict instead of raising, so one bad read never stops a cycle.

What happens inside every call

  1. Wait for the rate limiter (ActionGate): team bucket, and for writes the per-bot bucket too. Reads and writes have separate budgets, so heavy reading can never block posting.
  2. Count it in the budget ledger.
  3. Call the platform; retry if the error is temporary (with exponential backoff, default up to 3 retries).
  4. Turn the outcome into a result and log it to actions.jsonl.

How errors are handled

SituationWhat the Actuator doesresult.detail
Dry run on (the default)Logs the write, does not send it; ok=Truedry run: not sent
Platform throttles us (429)Tells the rate limiter to halve its speed, waits, retriesthrottled

Bad credentials (AuthError)Raises, on purpose: this must stop the run loudly—
Each bot is slow on purpose With the default config a single bot can write about once every 50 seconds (CTN_ACCT_WRITE_RPS=0.02), and the whole team about 0.15 writes/second. If you call two actions on the same bot back-to-back, the second one waits; it does not fail. Spread actions across bots (the loop already does this).

04Decision rules — ctn/pipeline/decide.py

One Decision per post, checked top to bottom; the first rule that matches wins.

#ConditionActionWhy

2Relevance < 1.5 (no keyword hit)observeNot about the referendum

Thresholds are constants at the top of decide.py (MIN_RELEVANCE, ALLY_ALIGNMENT, REPOST_MIN_ENGAGEMENT, COUNTER_MIN_REPLIES). Side detection uses SIDE_SIGNALS, a short list of hashtags/phrases per side.

Placeholder scoring Relevance and alignment are simple keyword checks, and SIDE_SIGNALS was guessed from the mock's hashtags. They store their output in the same JevAnswers format Jev will return, so when Jev is wired in, only the scoring changes. The rules above keep working.

05Our side: CTN_SIDE

The organisers have not assigned our side yet, so the side is a setting, not code.

Not set (default)

The loop still reads and makes decisions, but every decision is observe. No likes, reposts or replies are sent. Settings.validate() warns:
CTN_SIDE not set (yes/no); the bot loop will only observe

Set it when we know

Add one line to .env (or the environment):

CTN_SIDE=yes   # or: no

No code change needed. yes / no follow the mock's convention: +1 stance = YES.

In code it is the Side enum in models.py: Side.YES, Side.NO, Side.UNASSIGNED; side.opponent gives the other side.

06How to use

A. Run the bot loop

import asyncio
from ctn.config import Settings
from ctn.client.mock import MockLegitClient   # swap for the real adapter later
from ctn.pipeline import BotLoop
from ctn.telemetry import Telemetry

settings = Settings.load()                  # reads .env + environment
for w in settings.validate():
    print("warn:", w)

telemetry = Telemetry(settings.log_dir, settings.log_level)
loop = BotLoop.from_settings(settings, MockLegitClient(), telemetry=telemetry)

# one cycle, to inspect what it would do
report = asyncio.run(loop.run_cycle())
print(report.status, report.observed)
for r in report.results:
    print(r.kind, r.account, r.ok, r.detail)

# or keep going every 30 seconds until stopped
asyncio.run(loop.run_forever(interval_s=30))

from_settings() builds the rate limiter, budget ledger and Actuator for you. By default it uses accounts bot_001 … bot_040 (from CTN_BOT_ACCOUNTS); pass accounts=[...] to choose. Other options: keywords=, max_actions_per_cycle= (default 3), rng= (for repeatable runs). To stop run_forever cleanly, pass stop=asyncio.Event() and call stop.set().

B. Call actions directly

from ctn.actuator import Actuator
from ctn.ratelimit import build_gate, build_ledger

actuator = Actuator(client, build_gate(settings.rate), build_ledger(settings.budget),
                    telemetry=telemetry, dry_run=settings.dry_run)

result = await actuator.like("bot_001", post_id)
result = await actuator.comment("bot_002", post_id, "Good point.")
result = await actuator.retweet("bot_003", post_id)
if not result.ok:
    print("failed:", result.detail)
else:
    print(result.response)   # platform's reply, e.g. the new post id

If you already have a BotLoop, reuse its loop.actuator instead of creating a second one. Two actuators would have two separate rate limiters and could together exceed the platform limit.

Note: in dry run a cycle still reports status="acted", because the decisions were "executed" in dry-run form. Check result.detail == "dry run: not sent".

07Logs

When a Telemetry is passed in, everything is written as JSON lines to CTN_LOG_DIR (not committed to git).

FileContents
decisions.jsonlEvery decision the loop tried to act on: post, action, scores, rationale, bot, text
actions.jsonlEvery write attempt: kind, bot, target, ok, detail, latency, platform response
system.jsonlThrottle / suspension warnings, and one cycle metric per cycle from run_forever (status, counts, budget spent)

Use decision_id to join decisions.jsonl with actions.jsonl.

08Rate-limit recovery fix

Found while stress-testing the new loop against the mock (5% random errors, throttling on, one suspended bot).

Problem

Each time the platform throttled us, the rate limiter halved its speed, but nothing ever sped it back up. ActionGate.on_clean_interval() existed but was never called. In the stress run reads dropped from 100 to 0.195 req/s and one cycle took 32 s. With real defaults, nine throttles would leave the bot at its floor: one read every 15 minutes, permanently.

Fix

The Actuator counts throttles (actuator.throttles). After any cycle with no throttle, the loop calls actuator.recover(), which lets the team read and write rates rise again (×1.05 per clean cycle, never above the configured rate). Covered by test_gate_recovers_after_clean_cycles.

Still open (in ratelimit.py, not changed)
  • Recovery is slow: from the floor it takes about 120 clean cycles (~1 hour at 30 s per cycle) to get back to full speed.
  • Only the team-wide rates recover. A per-bot rate that was slowed down stays slow.
